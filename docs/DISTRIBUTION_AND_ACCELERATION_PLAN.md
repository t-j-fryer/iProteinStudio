# Distribution, engine extensibility and Apple GPU runtime plan

Research date: **19 September 2026**. This is the original architecture recommendation, not a current installation inventory.

**Implementation update, 20 September:** experimental PSICHIC is integrated locally; eleven portable engine-family candidates, activation recovery, per-job portable bindings and shared registry dispatch are implemented. Fresh-Mac, older-OS scientific qualification and GitHub package publication remain outstanding. See [current implementation and limits](PORTABLE_RUNTIME_IMPLEMENTATION.md) and [Lab Book 0177](../lab_book/0177-integrate-psichic-portable-runtimes.md). This review combines current
repository evidence with primary upstream documentation. It proposes changes
to software distribution and runtime validation, not to scientific defaults.

**Recommendation:** retain a small native macOS app; download independently
versioned, signed engine packages; preserve engine-specific dependency isolation;
select only validated hardware/OS profiles. Build native code on release machines,
not on users' Macs. Use GitHub Releases for executable packages and approved
upstream endpoints for model weights. Advance packaging and GPU optimization
as separate workstreams so their effects can be distinguished.

## 1. What exists and should be retained

The current application already separates Sparkle app updates from optional
engine/model installation. It has resumable checksummed downloads, staged runtime
activation, receipts, execution leases, immutable scientific plans, resident
workers and campaign script snapshots. These are foundations to extend.

The [source inventory](../lab_book/artifacts/0165-distribution-research/inventory.json)
was generated by executing its adjacent `inventory.py`. It records source hashes
and declared setup versions, not the state of every installed environment.

| Engine/runtime | Python selected by setup | PyTorch pin | MLX pin |
|---|---|---|---|
| Core MPNN | 3.11.13 | 2.2.1 | — |
| Boltz-2 | 3.11.13 | 2.13.0 | — |
| AntiFold | 3.10.18 | 2.2.0 | — |
| IntelliFold | 3.12.11 | 2.6.0 | — |
| Protenix v2/Mini | 3.11.13 | 2.7.1 | — |
| Protenix Constraint | 3.12.11 | 2.7.1 | — |
| LASErMPNN | 3.11.13 | 2.2.1 | — |
| OpenFold3 | 3.11.13 | 2.6.0 | 0.32.0 |
| NESSO | 3.12.10 | 2.11.0 | — |
| RFdiffusion3 | 3.12.11 | 2.13.0 | 0.32.0 |

The different versions explain why one shared, continually upgraded Python
environment would be fragile. Even matching Torch versions do not establish
compatibility: NumPy, Python ABI, native extensions and engine patches also matter.

Current gaps identified in source:

- Native builds remain in the unconditional MPNN installation, optional native
  extensions and Kalign. Git checkouts and editable installs remain client work.
- Fourteen `/usr/bin/python3` references occur in the inspected Core/pipeline
  helper/MCP paths. Some launch execution; others check availability or provide a
  fallback. Removing the setup compiler check would not remove these dependencies.
- RFdiffusion3 pins direct requirements and a source commit, but its installer
  uses `uv pip install -r` without the full hashed transitive lock used elsewhere.
- `Predictor.swift` and the setup shell script encode engines in switches and
  component-specific branches. Adding an engine currently touches many layers.
- `release_app.sh` uses reused version tags and `--clobber`. Future immutable
  publication must use unique release identities and refuse asset replacement.
- Campaign snapshots preserve scripts; the next design must also pin complete
  runtime closures so a later environment update cannot change a resumed job.
- CI currently uses a moving `macos-latest` label for fixture contracts. It is
  not evidence of clean-Mac installation or cross-generation GPU acceptance.

The local built 0.2.0/build 41 app contained **38,002,225 logical bytes in 302
regular files**, measured September 19; symlinks excluded. This is neither a DMG
download measurement nor an estimate for the proposed packages.

## 2. Distribution units and hosting

| Unit | Contents | Delivery/update policy |
|---|---|---|
| Native app | UI, bootstrap installer, compatibility resolver, project browser, trusted update keys | Developer ID signed/notarized app; Sparkle updates |
| Control runtime | Pinned portable Python and dependencies for the broker/orchestration | Small managed download during initial engine setup; app-compatible protocol |
| Engine package | Validated source/patches, complete runtime, native libraries, adapters, notices and receipts | Signed immutable release; installed only when needed |
| Model/data asset | Checkpoint, CCD or other shared reference data | Approved upstream URL/revision/hash; independently cached |
| Job record | Exact package/profile/model identities, parameters, MSA/input hashes and checkpoints | Local durable state; never rewritten to mean a newer runtime |

An engine release is a logical manifest, not necessarily one giant archive. It
can reference an unchanged runtime payload plus a small versioned adapter payload
and separate model assets. A wrapper/UI integration fix should reuse the existing
Torch/runtime bytes when its tested compatibility permits. Each payload remains
immutable and the exact combination is validated together. Do not unpack an
adapter update into an already signed runtime tree. This keeps ordinary updates
small without merging incompatible environments.

The native app must open projects and display installation status without Python.
Its first download cannot depend on a Python interpreter it has not installed.
Use native networking, verification and extraction for that bootstrap. Afterward,
all Python launch sites must resolve an exact managed executable, including MCP,
sequence parsing, job submission and diagnostic helpers. No PATH/Homebrew/system
Python discovery in the ordinary user path.

GitHub can host the app, control runtime, engine binaries and release manifests.
Use **Releases**, not Git checkouts, moving source-archive URLs, Actions artifacts
or Git LFS as the product installer. Publish all assets in a draft, verify them,
publish the immutable release, then update the signed discovery catalog. GitHub
supports immutable assets/tags and release attestations. Each release asset must
be below 2 GiB; keep packages below that limit or define individually hashed
parts. [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases),
[release limits](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

Use unique identifiers containing app build or engine package revision. A patched
package with unchanged upstream version still gets a new package ID. Existing
URLs never acquire different bytes. A small signed catalog can be served via a
static HTTPS endpoint, with immutable package URLs and approved mirrors. A later
CDN/object-storage move should change transport URLs, not package identities.

For general distribution, users should not need GitHub accounts. Public release
assets can be separate from a private source repository if distribution is
approved. Private evaluation assets require proper per-user authentication;
never embed a maintainer token. Existing institutional licensing restrictions in
[LICENSING.md](../LICENSING.md) still apply. No repository visibility change or
publication is part of this proposal.

**Do not redistribute model weights.** Keep approved upstream downloads separate,
including any access/terms flow. Hashes and mirrors must identify the exact same
asset. Different checkpoint variants remain different assets. Local conversions
record input hash, converter package/profile and output hash; they are not hidden
substitutions or preconverted weight uploads to our releases.

## 3. How to build portable engine packages

The release pipeline should assemble a complete dependency closure: exact Python,
all wheels, native helpers, upstream source revision, compatibility patches and
licenses. Source builds happen only in that controlled pipeline. Validate an
offline install from the wheel collection before assembling the runtime. Ordinary
users receive the resulting tested runtime and never resolve dependencies from
PyPI or execute package build backends.

Start with independently sealed runtime packages per compatible engine family.
They may include their own small Python distribution initially: reliability is
more valuable than premature deduplication. Use exact-byte download caching and
safe APFS cloning where applicable. Share Python or runtime layers later only
when relocation, signing and full dependency compatibility are demonstrated;
never share a writable site-packages directory. Models/reference data remain
separate and reusable from the start.

**Do not zip the developer's venv.** Python explicitly describes venvs as
non-portable; scripts and configuration commonly retain absolute paths.
Build a relocatable runtime layout using a pinned portable CPython distribution,
with verified relative library paths and an explicit launch wrapper. Astral's
python-build-standalone is a relevant existing foundation, already used by uv.
[Python venv documentation](https://docs.python.org/3/library/venv.html),
[uv Python distributions](https://docs.astral.sh/uv/concepts/python-versions/).

Relocation must finish before signing. Inspect all Mach-O dependencies and rpaths
for developer paths, Homebrew libraries, Apple SDK linkage that should not ship,
and incorrect deployment targets. Launch using an executable plus argument array,
not shell activation or fragile console-script shebangs. Test spaces, Unicode,
different usernames and directories without build tools. Keep imports, JIT/Numba
caches, logs and generated data out of signed package trees. Disable accidental
user-site/PYTHONPATH injection while preserving explicitly allowed model/cache
locations. Do not expect a raw wheel tag to prove every embedded binary is
compatible with an older macOS release.

If a sealed runtime cannot pass these relocation/signing tests, a fully locked
wheel-only local assembly is a possible transitional design, but it must also
prove that installation preserves native signatures and introduces no source
builds. It is not a reason to fall back silently to compilation.

## 4. Trust, notarization and publication

Sparkle protects the app update path; it does not automatically authenticate
engine downloads. Engine catalogs need their own pinned signing trust, schema
validation, package hashes, monotonically versioned metadata, key rotation and
withdrawal rules. Sign the exact catalog bytes and define verification explicitly;
do not assume JSON reserialization preserves a signature. Separate package signing
from ordinary repository write access. Preserve a known-good catalog for offline
use; stale update metadata must not invalidate already-installed jobs.

Sign and notarize downloaded executable payloads as well as the app. Apple
explicitly addresses network installers and their separately notarized downloads.
Use an appropriate staplable distribution container and verify the extracted
payload, including Python, extensions and dynamic libraries. Sign nested code
before enclosing bundles; give only the executable needing JIT any necessary
entitlement. Test library validation instead of disabling it globally. The current
deep-signing release shortcut is not a completed runtime-signing design.
[Apple network-installer notarization](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow),
[notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).

Signed metadata and Apple notarization address different trust boundaries. Both
belong in the release process. Neither justifies removing quarantine or weakening
Gatekeeper. Relocation/extraction must reject escaping paths and symlinks, preserve
intended modes and fail closed on corrupted packages. Record an SBOM and build
provenance; retain dependency notices and required source/license materials.

Build/test untrusted pull requests without signing secrets. Promotion/signing
runs only for approved commits on protected release jobs. Existing model files,
private test inputs and API credentials never become release assets.

## 5. Installation and updates a scientist can understand

The first-run screen should ask what the user wants to do, then recommend the
smallest validated set for that workflow and Mac. Do not force sequence-design
dependencies on someone who only wants prediction. Show compatible alternatives
without exposing Python or ABI decisions as user choices.

Before downloads, check native Apple Silicon execution, actual GPU availability,
macOS support, RAM and available storage. Present three distinct quantities:
download remaining, added installed space, and temporary space required while
preserving the old version. Derive these from release manifests and cache state;
the current rounded engine budgets are not sufficient for exact installation.

One review/Install action authorizes the displayed component plan. Progress should
say downloading, verifying, preparing or checking readiness. A brief deterministic
GPU diagnostic can detect unsupported/broken operations; scientific readiness
requires the engine's declared smoke test too. If an optional component fails,
keep successful ones available and offer Retry for the failed component. Preserve
partial downloads through disconnects, sleep, app quit and restart. Show a concise
reason, repair action and support-report export rather than a raw terminal log.

Users should see engine name, purpose, readiness, compatibility and storage. Keep
package versions and diagnostics available in details. No Terminal, GitHub login
for public assets, administrator rights for per-user runtimes, or developer tools
should be required for the supported path. An installation on a locked-down
institutional Mac may still require its administrator's software approval.

After installation, local workflows can operate offline when their required
assets and alignments are available. Do not promise that remote alignment services
work offline. Support verified offline package import for restricted labs, with
the same authenticity and license rules; never bundle project data or restricted
weights into a general installer export.

## 6. Runtime updates must preserve experiments

Use an explicit state machine:

```mermaid
flowchart LR
  A[Resolve compatible package plan] --> B[Download to staging]
  B --> C[Verify signature and hashes]
  C --> D[Extract and validate runtime]
  D --> E[GPU and engine readiness checks]
  E --> F[Activate for new jobs]
  F --> G[Retain previous version for rollback]
```

No dependency or shared asset is overwritten in place. Treat a compatible set of
packages as one activation transaction. Existing atomic helpers are useful, but
the multi-package path needs a persistent journal and recovery from termination
between filesystem operations. Exception handling alone is not crash recovery.

Every queued/running/resumable job retains absolute immutable package locations
and a resolved graph digest, not a `current` symlink. Pin worker protocol, adapter,
Python, tensor runtime, precision profile, checkpoint and reference data. Keep
the broker compatible with existing job records or pin its runnable snapshot too.
The GUI, CLI and MCP must resolve the same registry and execution lock; no
alternative fast path bypasses plan/script provenance.

App updates may download separately, but a restart/activation must respect active
work. Engine updates install alongside the old version; adoption for new jobs
follows the reviewed update plan. Preview optimization profiles remain opt-in.
Resume never silently migrates runtimes. Cleanup reports space recoverable and
retains packages referenced by active or explicitly retained resumable jobs.
Archiving results and retaining exact replay environments are distinct choices.

Capture macOS build, device/Metal capabilities, package hashes and precision
settings in every run. A pinned environment cannot pin Apple's driver across an
OS update, and cross-device stochastic results are not necessarily bit-identical.
State that limit rather than promising impossible reproducibility.

## 7. Extensibility through a versioned engine contract

Introduce a curated engine registry and out-of-process adapters. Avoid native
plug-ins loaded into the Swift UI and avoid a universal Python environment. A
process boundary isolates dependencies/crashes; it is not a security sandbox.
Initially accept only project-approved signed engine packages, with any local
development override explicitly separated from the user distribution.

| Manifest area | Required information |
|---|---|
| Identity | Stable engine ID, package revision, source/patch hashes, channel |
| Compatibility | App and worker protocol ranges, architecture, tested OS/device profiles, Python/native ABI |
| Capabilities | Supported workflows/input types, templates/MSA support, exposed settings and constraints |
| Artifacts | Immutable URLs/mirrors, byte counts, hashes, signature identity, dependency IDs, licenses |
| Execution | Entrypoint, request/result schemas, resource limits, cancellation/resume semantics |
| Outputs | Coordinate/confidence artifacts, metric definitions/units, optional versus required fields |
| Acceptance | Import/operation checks, benign engine smoke fixture, numerical validation reference |

Requests and events need schema versions and stable job IDs. Existing JSON/MCP
contracts are the starting point. Support progress, structured errors, checkpoints,
results and cancellation. Capability declarations must be validated against the
adapter's actual behavior. Keep arbitrary shell commands and remote UI code out
of catalog metadata. Unknown capabilities produce a clear app-update requirement.

Preserve stable IDs from old projects, including retired engines; avoid breaking
decoding when moving away from the closed `Predictor` enum. Generic settings can
be rendered from a constrained schema, while substantial new scientific workflows
still deserve explicit UI work and an app release. This is extensibility without
pretending every future feature can be added safely through a manifest.

Expected change paths:

- New checkpoint supported by an existing adapter: model entry and validated
  compatibility record; no giant app re-download.
- Engine bugfix/runtime upgrade: new package revision and acceptance results;
  preserve old package for existing work.
- New predictor using an existing request/result contract: adapter, package,
  catalog and tests; minimal or no native UI change after registry migration.
- New workflow or output concept: versioned schema plus app/MCP support, followed
  by compatible engine packages.

## 8. What current Apple GPU developments mean

PyTorch **2.14.0**, released September 2, is the current stable release observed
in this review. Version 2.13 expanded native Metal kernels and added MPS
FlexAttention. Version 2.14 adds further native operations, linear algebra and
allocator/copy changes. Its new MPP attention path is conditional on macOS 26.2+,
half/bfloat16 inputs and supported shapes; it is not a universal acceleration
switch. These are upstream capabilities, not measured Studio gains.
[PyTorch releases](https://github.com/pytorch/pytorch/releases),
[2.13 announcement](https://pytorch.org/blog/pytorch-2-13-release-blog/),
[2.14 announcement](https://pytorch.org/blog/pytorch-2-14-release-blog/).

M5 has matrix accelerators inside its GPU cores. These **GPU Neural Accelerators
are distinct from the Apple Neural Engine**. Modern MLX/Metal paths can use them
without moving the model into a separate ANE backend. Apple's MLX discussion
requires macOS 26.2+ for the M5 acceleration path and benchmarks LLM workloads;
those results cannot be extrapolated into a protein-prediction speedup.
[Apple M5 architecture](https://www.apple.com/newsroom/2025/10/apple-unleashes-m5-the-next-big-leap-in-ai-performance-for-apple-silicon/),
[Apple MLX/M5 research](https://machinelearning.apple.com/research/exploring-llms-mlx-m5).

MLX **0.32.2** is the latest release observed; both current MLX engine locks use
0.32.0, so MLX adoption itself is not missing. New releases include targeted
attention/Neural-Accelerator work and correctness fixes. Audit precision as well
as version: current MLX documentation says `MLX_ENABLE_TF32` permits reduced-
precision float32 matrix operations by default on supported hardware. A tensor
being labelled float32 does not by itself establish full-precision computation.
Record and validate that policy; do not silently change existing campaigns.
[MLX releases](https://github.com/ml-explore/mlx/releases),
[MLX precision controls](https://github.com/ml-explore/mlx/blob/v0.32.2/docs/src/usage/precision.rst).

Retain **PyTorch/MPS and MLX** where upstream engines support them. A blanket MLX
rewrite would create another scientific port to validate and maintain. Core ML/ANE
conversion is a separate deployment project; it is not enabled by changing a
PyTorch device flag. Whole-model compilation, custom Metal kernels and reduced
precision are later engine-specific candidates, not installation defaults.
Any optimization invoking an external compiler on first use would reintroduce
the developer-tools problem and needs to be precompiled or excluded from the
normal profile. OS-provided runtime shader compilation is a different mechanism.

Also distinguish GPU acceleration from available memory and bandwidth. Newer base
chips do not automatically outperform every older Max/Ultra on every workload.
Avoid chip-name speed rankings until end-to-end measurements exist.

## 9. Optimization order and validation

**First evaluate a separately packaged PyTorch 2.14 Boltz profile**, preserving
the current scientific settings and adapter behavior for the comparison. This is
a small runtime-version step with potential correctness as well as performance
benefits. Studio's older M1 incident motivated an allocator mitigation; the
upstream issue remains open and describes later allocator behavior as masking,
not proving the underlying fault fixed. Do not remove that mitigation merely
because 2.14 is newer.
[Local M1 investigation](../lab_book/0061-finish-m1-predictor-correctness.md),
[upstream issue 193487](https://github.com/pytorch/pytorch/issues/193487).

Then assess NESSO and the larger IntelliFold/Protenix runtime gaps in separate
environments, and MLX 0.32.2 for the already-MLX engines. Keep the legacy
MPNN/AntiFold/LASErMPNN environments intact until their dependencies and native
extensions are rebuilt and checked. This ordering is engineering judgment based
on version gaps and known issues, not a measured ranking of possible speedups.

Keep FP32 profiles where currently validated. Evaluate runtime upgrades before
changing dtype, attention implementation, batching or model settings. The new
half-precision attention path will not automatically accelerate a forced-FP32
workload. FlexAttention's presence does not establish a benefit for dense or
pair-biased model attention. Native GPU SVD is worth checking where an adapter
currently uses a documented CPU operation, but remove only that tested workaround.
Do not enable global CPU fallback, fast math or unlimited GPU allocation to make
a test pass. [PyTorch MPS controls](https://docs.pytorch.org/docs/2.14/mps_environment_variables.html).

Preserve resident workers and measured scheduling. Profile startup, loading,
feature preparation, CPU/GPU transfers, inference, scoring and output separately;
a faster kernel may have little effect on a job dominated by another stage.
Benchmark cold and warm execution, peak/resident memory, first-result latency,
sustained throughput and cancellation/resume, under matched inputs/settings.
Use benign software-regression fixtures, record actual hardware/OS, and keep
upstream or synthetic kernel benchmarks explicitly separate from Studio results.

Acceptance needs more than import success or a plausible confidence score:
finite tensors/coordinates, output cardinality, numerical tolerances against a
declared reference, structural sanity, repeated allocator-state tests and longer
memory/restart runs. Tolerances must be defined per computation rather than
requiring bitwise equality across devices. Promote profiles only with recorded
evidence; install-time checks detect compatibility, not general scientific validity.

## 10. Compatibility and release test matrix

Preserve the current macOS 14 app floor as a product target, but declare each
engine package's actual tested minimum separately. A package built for a newer
OS is not compatible just because the app opens. Prefer one baseline arm64 build
with runtime capability dispatch where it works; add extra packages only when
ABI/OS constraints or validated gains justify them. Avoid multiplying every
engine into M1/M2/M3/M4/M5-specific builds unnecessarily.

| Dimension | Acceptance coverage |
|---|---|
| Clean installation | Standard user; no CLT/Xcode/Homebrew/Python; browser-downloaded quarantined app |
| Hardware | At least an older M1-class device and an M5-class device; reference M4; low-memory case |
| OS | Oldest claimed version per package; current supported version; relevant accelerator API boundary |
| Filesystem | Different usernames; spaces/Unicode; read-only app; low disk; supported external-volume behavior |
| Network | Disconnect/resume, proxy/TLS handling, unavailable upstream, expired gated URL, cache/offline import |
| Trust | Corrupt archive, invalid signature, wrong architecture, escaping extraction path, withdrawn package |
| Lifecycle | Crash during each install/activation stage; app upgrade; active/queued/resumable jobs; rollback/cleanup |
| GPU | Required operation diagnostics and benign real-engine smoke; repeated numerics and memory checks |
| Extensibility | Older app versus newer catalog; old projects/metrics; missing optional outputs; worker protocol mismatch |

GitHub Actions can build arm64 binaries and run contracts. Its runner labels and
hardware are not a substitute for the claimed device matrix. Pin runner/SDK
configuration and record actual images; use tested GPU-capable hosted hardware
where available and protected physical M1/M5 test machines for decisive acceptance.
Many hosted runners already include developer tools, so ordinary CI success does
not demonstrate a clean installation. Never run untrusted fork code on machines
holding release secrets or private scientific data.
[GitHub runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).

## 11. Migration sequence and concrete deliverables

| Stage | Deliverable | Exit condition |
|---|---|---|
| 1. Freeze the specification | Versioned package/catalog/worker schemas; exact runtime inventory and source hashes | One authority for compatibility and provenance; no engine upgrades yet |
| 2. Prove packaging | Control runtime plus current core MPNN and one current predictor; portable signed packages | Clean older/current Macs install and run without developer tools; no scientific pin changes |
| 3. Complete the installer | Native bootstrap, managed interpreter resolution, journalled activation, rollback, exact storage accounting | Interrupted installation and app/runtime update tests pass; current installs can migrate non-destructively |
| 4. Expand engine coverage | Remaining packages, fully locked RFdiffusion3 graph, upstream model manifests | Every exposed engine has a tested package or a clear unavailable state; no compilation fallback |
| 5. Introduce registry/adapters | Stable IDs, capability-driven UI and common GUI/CLI/MCP contracts | Add a representative engine without editing a large set of switches; old projects still load |
| 6. Promote performance profiles | Isolated Torch/MLX candidate packages and recorded cross-Mac results | Correctness, memory, restart and performance acceptance; user-visible update notes |

Performance evaluation can proceed alongside packaging, but do not bundle both
changes into an unexplainable first migration. First prove the new distribution
with current pins, then offer validated accelerated revisions. Keep the existing
working environments during transition; source installation remains a separate
developer workflow and never an invisible repair strategy for ordinary users.

The first implementation should be a complete small vertical slice, including
GitHub draft artifacts and a clean-machine install, before redesigning every
engine. Exact future download/storage sizes, M5 speedups and implementation time
remain unmeasured. This report does not authorize publishing releases, alter
existing runs or certify the proposed compatibility matrix as passed.
